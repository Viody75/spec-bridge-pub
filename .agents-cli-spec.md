# SpecBridge Agent — Agent Specification

## Overview

SpecBridge Agent is a backend-only, multi-agent analysis service that turns project notes into traceable PRD/SRS drafts and a Requirements Traceability Matrix (RTM). The service accepts normalized JSON plus direct PDF, DOCX, TXT, and Markdown uploads. PDF/DOCX text extraction runs locally in the same service before entering the normalized-source workflow; source-system connectors remain outside the MVP.

One Google ADK graph workflow runs all stages in a single Python deployment. It extracts candidate requirements, links them to prior requirements and sources, runs five specialist reviews, conducts a bounded structured debate, detects unresolved conflicts, and writes a draft document. Human Product Owners remain accountable for manual additions, conflict decisions, and final publication.

The MVP deliberately limits the initial slice to one fixed workflow, one Cloud Run service, local text extraction, normalized text input, two debate rounds, PostgreSQL persistence, and a thin integration with the existing Next.js frontend. Direct Slack/Teams/Jira ingestion, OCR, MCP, and production CI/CD are deferred.

## Language

Python 3.11+ with Google ADK and FastAPI.

The existing SpecBridge frontend remains Next.js and TypeScript. It consumes the backend through a same-origin Next.js API proxy so the shared development API key is never embedded in browser JavaScript. When the backend URL is absent, the existing demo-data service remains available as an explicit local fallback.

## Frontend Integration Slice

The first end-to-end integration exposes a project workspace aggregate rather than duplicating one endpoint per visual component. It supplies projects, normalized sources, current requirement revisions and trace links, the latest agent run, specialist findings, moderator output, conflicts, and the latest document version. Frontend adapters map this backend contract into the existing page types.

The slice includes project creation, direct PDF/DOCX/TXT/Markdown upload, normalized-source submission, synchronous analysis, manual requirements, immutable human edits, human review, implementation-status updates, conflict decisions, and guarded publication. Uploaded documents are extracted in memory and converted into the same normalized JSON contract before the agent workflow runs. Scanned/image-only PDFs are rejected with an OCR-required error in this MVP.

Agent stage names and run status are treated as a public product contract for the frontend activity and audit views. Human approval rules remain deterministic backend checks rather than LLM decisions.

## Architecture & Agents

The backend will be created as a separate `specbridge-agent/` project and deployed as one Cloud Run service.

The root agent is a deterministic ADK graph `Workflow`, not a free-form LLM coordinator. Its flow is:

1. Validate and persist the normalized source payload.
2. Extractor Agent creates candidate requirements and exact source citations.
3. Trace Linker performs project-scoped hybrid retrieval against existing requirements.
4. Five specialist agents perform an initial review in parallel.
5. A join step collects all findings without suppressing minority opinions.
6. The five agents perform one parallel rebuttal round against relevant findings.
7. Moderator Agent decides whether the result is consensus, unresolved dissent, or requires human context.
8. Conflict Detector records contradictions within and between requirements.
9. Document Writer produces a draft PRD or SRS and RTM revision.

The workflow has at most two deliberation rounds: initial review plus one rebuttal. It must then continue with recorded dissent or escalate to the Product Owner; it must never loop indefinitely.

### Agent responsibilities

- **Extractor Agent** — identifies candidate requirements from normalized sources; preserves quotations and locators; distinguishes explicit statements, inferred needs, and assumptions.
- **Trace Linker Agent** — classifies each candidate as `new`, `updates`, `duplicates`, or `possibly_conflicts` using exact/fuzzy matching and stored embeddings.
- **Business Analyst Agent** — reviews necessity, correctness, completeness, terminology, and source alignment.
- **Project Manager Agent** — reviews scope, value, schedule implications, dependencies, and risks.
- **Developer Agent** — reviews technical feasibility and constraints while keeping requirements focused on *what* rather than prematurely prescribing *how*. Architecture or technology proposals require explicit alternatives and trade-offs.
- **Quality Assurance Agent** — reviews verifiability, measurability, consistency, and ambiguity.
- **Designer Agent** — reviews usability, accessibility, user workflow, and user-impact risks.
- **Moderator Agent** — neutrally synthesizes agreements and disagreements, challenges unsupported claims, applies stopping rules, preserves dissent, and escalates missing context. It cannot silently choose a majority opinion.
- **Conflict Detector** — identifies conflicts between requirements, sources, standards, policies, assumptions, and reviewer findings.
- **Document Writer** — creates only draft PRD/SRS and RTM revisions from accepted workflow outputs; it cannot resolve conflicts or publish a final version.

## Structured Deliberation Contract

Every agent-created content item, finding, rebuttal, and recommendation must use a validated schema containing:

- `claim`
- `rationale`
- `evidence_refs`
- `role_perspective`
- `standard_refs`
- `assumptions`
- `alternatives_considered`
- `confidence`
- `dissent`

Role-play experience is a professional heuristic, not evidence. An agent must not present invented experience, sources, regulations, project facts, or implementation constraints as factual. Unsupported proposals must be marked as assumptions and routed to the Product Owner when material.

## Standards and Project Policy

Review criteria start with the configured interpretation of ISO/IEC/IEEE 29148 section 5.2.5 and the role criteria above. The exact PRD/SRS scope is limited to the active, versioned standards and project policy.

The future SCM Plan is represented in the MVP as versioned project policy data rather than hard-coded prompt text. A policy version can define responsibility, required reviewers, approval authority, document sections, review rules, and additional quality criteria. Changing policy creates a new version and applies only to subsequent runs unless a human explicitly requests re-analysis.

## Input Contract

The service accepts either normalized JSON or a raw `.pdf`, `.docx`, `.txt`, or `.md` upload. Raw uploads are size-limited, normalized in memory, and then passed to the same analysis contract. Each JSON analysis request includes a project identifier, target document type, and one or more normalized sources.

Example:

```json
{
  "project_id": "silp",
  "document_type": "PRD",
  "sources": [
    {
      "source_id": "po-notes-017",
      "source_type": "pdf",
      "title": "Catatan Kasar Product Owner",
      "author": "Dimas Pratama",
      "occurred_at": "2026-10-20T09:00:00+08:00",
      "content": "Normalized source text",
      "locator": {
        "page": 4,
        "paragraph": 2
      },
      "metadata": {}
    }
  ]
}
```

Supported normalized source types initially include `pdf`, `docx`, `meeting_transcript`, and `manual_note`. The schema is extensible to additional normalized source types. A locator can use page/paragraph coordinates for documents or timestamp/speaker coordinates for transcripts.

Source content is untrusted data. Text inside a source must never override system instructions, policies, permissions, tool constraints, or approval rules.

## Output Contract

A successful synchronous analysis returns and persists:

- the analysis run identifier and status;
- extracted requirement candidates and their source links;
- trace-link classifications and confidence;
- all initial findings from all relevant reviewers;
- all rebuttals and Moderator rationale;
- consensus and unresolved dissent;
- detected conflicts and their affected items;
- draft PRD/SRS sections;
- draft RTM rows;
- token/model usage metadata suitable for cost tracking.

All workflow-node inputs and outputs use Pydantic models. Invalid model output is rejected or retried within a fixed bound rather than silently accepted.

## API Surface

- `GET /health` — unauthenticated health check with no sensitive details.
- `POST /v1/projects` — create project and initial policy.
- `POST /v1/projects/{project_id}/sources` — persist normalized sources.
- `POST /v1/projects/{project_id}/uploads` — extract one PDF/DOCX/TXT/Markdown file and synchronously run analysis.
- `POST /v1/projects/{project_id}/requirements/manual` — add a human-authored draft requirement.
- `POST /v1/projects/{project_id}/analysis` — synchronously run the bounded workflow and return the complete result.
- `GET /v1/projects/{project_id}/analysis/{run_id}` — retrieve a persisted run for audit or reconnection.
- `POST /v1/conflicts/{conflict_id}/decisions` — record a Product Owner decision and rationale.
- `POST /v1/documents/{document_id}/publish` — publish a draft only after all required human gates pass.

All `/v1` endpoints require an `X-API-Key`. The Cloud Run service is publicly reachable during MVP development; only `/health` is intentionally unauthenticated.

## Data Sources, Storage, and Tools

- **Vertex AI Gemini** — use a cost-efficient Gemini Flash-family model for agent reasoning. The exact model version must be selected from models actually available to the GCP project at implementation time.
- **Vertex AI text embeddings** — generate an embedding only when requirement content is created or changed.
- **Neon PostgreSQL** — authoritative store for projects, policies, normalized sources, requirements, revisions, trace links, reviews, rebuttals, conflicts, human decisions, document versions, analysis runs, and audit events.
- **Neon `pgvector`** — project-scoped similarity search over existing requirements.
- **Typed Python tools** — parameterized database access, hybrid retrieval, persistence, and policy loading. MCP is intentionally deferred.

Hybrid trace linking combines exact identifier matching, normalized/fuzzy text matching, and vector similarity. Only a small top-k set from the same `project_id` is sent to the LLM for final classification. Embeddings are reused until content changes.

The Neon connection string and API key must be stored in GCP Secret Manager and injected as environment variables. Secrets must never be committed, returned in API responses, or written to logs. The database credential previously shared during design must be rotated before deployment.

## Persistent Model

The MVP data model must cover at least:

- projects and versioned project policies;
- normalized sources and source locators;
- requirements and immutable revisions;
- requirement-to-source trace links;
- analysis runs and stage status;
- specialist findings and rebuttals;
- moderator decisions and unresolved dissent;
- conflicts and human decisions;
- documents, document sections, versions, and RTM rows;
- audit events and model-usage metadata.

Human-authored requirements use `source_type=human_manual`. Agents may review them and propose a new revision but may not overwrite the human-authored revision.

## Constraints & Safety Rules

- Conflict resolution and final publication always require an explicit Product Owner action.
- Agent findings are advisory; no reviewer can directly mutate an accepted requirement.
- All database access is parameterized and scoped by `project_id` where applicable.
- Source text is treated as untrusted content and cannot issue instructions to the workflow.
- Every mutation produces an immutable revision or audit event.
- All reviewer findings, including minority dissent, remain visible and queryable.
- The Moderator cannot claim consensus when a blocker or material unsupported assumption remains.
- The workflow is limited to two deliberation rounds.
- Model calls have per-stage timeout, retry, output-token, and total-run budgets.
- Logs contain identifiers and operational metadata, not source content or secrets by default.
- The service rejects oversized payloads before calling a model.
- API-key comparison is timing-safe; secret values are never stored in plaintext application tables.
- Production publication is blocked if required review, traceability, conflict, or approval conditions are incomplete.

## Cost and Performance Controls

- Use a Gemini Flash-family model initially; use a larger model only after evaluation demonstrates a specific quality gap and a human approves the change.
- Run the five reviewers and rebuttal agents concurrently with bounded workflow concurrency.
- Give reviewers requirement-specific evidence, not the entire source corpus.
- Cache and reuse embeddings until requirement text changes.
- Restrict vector retrieval by project and top-k.
- Use one initial review and one rebuttal only.
- Use synchronous execution for MVP and avoid Cloud Tasks, Pub/Sub, MCP, Vertex AI Search, GKE, and additional vector services.
- Persist model name, token counts, duration, and retry counts per stage for later cost analysis.

## Deployment

- Target: Google Cloud Run in `asia-southeast1`.
- Model endpoint: Vertex AI `global` is allowed.
- Container: one Python/FastAPI/ADK service.
- Access: publicly reachable during MVP development, protected by `X-API-Key` for all business endpoints.
- Database: external Neon PostgreSQL with SSL and `pgvector`.
- Deployment workflow: manual, wrapped in a single `make deploy` command.
- `make deploy` must run configuration validation, code tests, and the agreed evaluation gate before invoking `agents-cli deploy`; the actual deployment still requires explicit human confirmation.
- CI/CD is not part of the MVP.

## Example Use Cases

### Rough Product Owner notes

Input: normalized text from a PDF or DOCX containing incomplete and informal notes.

Expected outcome: candidates distinguish explicit requirements from inferred needs and assumptions; reviewers challenge ambiguity; missing business context is escalated rather than invented; the output is a traceable draft.

### Meeting transcript with disagreement

Input: normalized transcript containing conflicting timeout expectations from Security and Customer Service.

Expected outcome: both positions and exact quotations are preserved; reviewers debate feasibility, usability, risk, and verifiability; the conflict remains open with options and rationale until a Product Owner decides.

### Existing requirement update

Input: new notes that alter a previously stored delivery-time target.

Expected outcome: hybrid retrieval links the candidate to the earlier requirement, records a proposed revision instead of a duplicate, preserves both source chains, and triggers a new bounded review.

### Human-authored draft item

Input: a Product Owner manually adds a draft requirement.

Expected outcome: it is stored with human provenance; agents review and may propose revisions, but the original human revision remains immutable.

### Technology recommendation

Input: project context requests an architectural or technology decision.

Expected outcome: the Developer and other affected roles compare alternatives, constraints, risks, and trade-offs; the Moderator produces a synthesis with explicit assumptions and dissent rather than an unsupported recommendation.

## Success Criteria

- 100% of agent-created requirements contain at least one valid `evidence_ref` or are explicitly marked as an assumption/proposal.
- 100% of requirements reviewed by the workflow receive a verdict from all five specialist roles; a role that finds no issue must still return an explicit `approve` verdict with rationale.
- 100% of agent claims and rebuttals contain a structured rationale.
- No run exceeds the two-round deliberation limit.
- 100% of unresolved blockers are recorded and escalated to the Product Owner.
- 0 conflicts are automatically resolved and 0 documents are published without the required human action.
- 100% of persisted workflow outputs pass their Pydantic schema.
- Trace Linker reaches at least 0.80 precision on the initial held-out evaluation cases.
- Role adherence, response quality, rationale quality, and traceability each score at least 0.80 in agent evaluation.
- Safety and human-approval-gate evaluations score 1.00.
- For the agreed benchmark payload of at most 25,000 normalized characters, end-to-end analysis has a target p95 latency of no more than 180 seconds under MVP test concurrency.
- Local validation, evaluation, and an approved deployment can be initiated through documented one-command Make targets.

Evaluation starts with 1–2 core cases, iterates until they meet the bar, then expands to conflict, ambiguity, prompt-injection, manual-entry, and technology-justification cases. A held-out subset must remain outside the prompt-tuning loop.

## Assumptions

- Direct uploads support text-based PDF, DOCX, UTF-8 TXT, and Markdown. OCR, audio, video, and image extraction remain outside the MVP.
- MVP requests contain at most 50 normalized sources and 100,000 normalized characters; larger inputs are rejected until chunking limits are validated. The 180-second performance target applies only to the 25,000-character benchmark payload.
- Only one active analysis run per project is allowed initially to avoid conflicting revisions.
- During the public-development MVP, a caller holding the shared API key is trusted to submit a Product Owner action. Each decision must include and audit an `actor_id`, but that identity is not cryptographically verified until OIDC/JWT authorization is introduced.
- The exact Gemini Flash and embedding model identifiers will be chosen from the models available to the configured GCP project and endpoint; they are not hard-coded in this design.
- The initial project policy encodes the agreed ISO/IEC/IEEE 29148 section 5.2.5 interpretation and role criteria; the SCM Plan can replace or extend it through a new policy version.
- Deployment uses an existing GCP project with billing, Vertex AI, Cloud Run, Cloud Build, Artifact Registry, and Secret Manager available or enableable.
- The database credential shared during the design conversation will be rotated before any environment is deployed.
